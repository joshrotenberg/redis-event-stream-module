# Higher-concurrency AWS ramp probe: 2026-07-30

This probe increased concurrency and run length while preserving the first
smoke run's server, images, payload, keyspace, and scenarios. It is a second
directional sample, not a statistically significant capacity result.

## Environment

- Region and zone: `us-west-2`, `us-west-2a`
- Server: `c7i.large`
- Load generator: `c7i.large`
- Redis/module image:
  `ghcr.io/joshrotenberg/redis-event-stream-module:0.4.0@sha256:1466a273fd64321ca3eba4447db3a16e2eb231be2afdb3a620c5cb2229be4db2`
- Load-generator image:
  `redis:8.8.0@sha256:234c902a2db49461a129e2d4aeff85b28cf20187ed274a67f6e50995fa713c7b`
- Workload per scenario: 5,000,000 `SET` requests, 200 clients, four load
  threads, 64-byte values, and a 100,000-key keyspace

The first run used 1,000,000 requests, 50 clients, and two load threads. All
other listed workload and environment settings were the same.

## Results

| Scenario | Operations/s | Change from ramp baseline | p50 | p95 | p99 | Maximum |
|---|---:|---:|---:|---:|---:|---:|
| `s0` module not loaded | 188,487 | baseline | 0.783 ms | 1.599 ms | 2.607 ms | 16.095 ms |
| `s1` module loaded, `SET` filtered | 186,720 | -0.94% | 0.855 ms | 1.511 ms | 2.087 ms | 218.879 ms |
| `s2` capture every `SET` | 118,892 | -36.92% | 1.559 ms | 2.031 ms | 2.271 ms | 220.671 ms |

All 5,000,000 selected events were forwarded in `s2`.
`events_lost`, `dropped`, and `handler_panics` remained zero, and the configured
`MAXLEN` held `events:set` at 10,000 entries. In `s1`, all 5,000,000
notifications were counted as filtered and no stream entries were written.

## Comparison with the first run

| Scenario | First run | Ramp probe | Change |
|---|---:|---:|---:|
| `s0` module not loaded | 137,912 ops/s | 188,487 ops/s | +36.67% |
| `s1` module loaded, `SET` filtered | 137,893 ops/s | 186,720 ops/s | +35.41% |
| `s2` capture every `SET` | 121,183 ops/s | 118,892 ops/s | -1.89% |

The unloaded and filtered cases benefited substantially from the added clients
and load threads. Full capture did not: it remained near 120,000 operations per
second. This is evidence that the capture configuration is close to a
throughput plateau on this hardware, while the first run did not fully drive
the baseline server. It does not prove which resource or capture sub-operation
is responsible because this probe did not collect CPU profiles or server
resource metrics.

The filtered-module throughput remained within 1% of the unloaded baseline even
after processing five million notifications. The full-capture penalty therefore
appears to be in forwarding, encoding, stream insertion, or trimming rather than
the notification filter gate.

The two module-loaded scenarios each recorded one maximum-latency outlier around
220 ms, despite p99 remaining between 2.0 and 2.3 ms. The first run did not show
these outliers. A single ordered run cannot distinguish module behavior from
load-generator scheduling, host noise, or another transient, so this should be
measured in repeated trials before being treated as a module defect.

## Next useful measurement

Repeat several shorter trials at client counts around 50, 100, 150, and 200,
randomize scenario order, and collect Redis process CPU plus load-generator CPU.
That would locate the knee more precisely, test whether the outliers reproduce,
and show whether the server or generator is limiting each scenario.
